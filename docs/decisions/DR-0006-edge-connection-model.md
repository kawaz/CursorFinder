# DR-0006: エッジ接続モデル — v2 PassSegment ペア方式を土台に V3 の知見を統合

## 背景

エッジ越境の表現方法が世代ごとに異なる:

- **V3 (MoonBit)**: `EdgeType` enum 4 値 (PP/PB/BP/BB) + `EdgePair` (EdgeSegment a/b + rate マッピング)。ただしレビューで「PB (ネイティブ通過可→仮想ブロック) をモデルで表現する手段がない」ことが Critical 判定された (virtual_edges は通過可能な接続しか持てず、PB/BB は force_block の実行時変換でしか発生しない)
- **v2 (LaserGuide 現 HEAD)**: `PassSegment` (id + pairedSegmentId + logical/physical range + invertRatio) を「OS 由来の自動生成 (`osPassSegments`)」と「ユーザ編集 (`passSegments`)」の 2 リストで持つ

v2 方式は集合の差分で 4 状態を全て表現できる:

| 状態 | osPassSegments | passSegments |
|---|---|---|
| PP (両方通過) | あり | あり |
| PB (OS 通過・仮想ブロック) | あり | **なし** |
| BP (OS ブロック・仮想通過) | なし | あり |
| BB (両方ブロック) | なし | なし |

つまり V3 の Critical「PB 表現不能」は v2 のデータモデルが既に解いている。

## 決定

**v2 の 2 リスト差分方式を土台とし、V3 の設計知見を以下の形で統合する。**

1. **EdgeType enum は永続モデルから外し、判定結果 (derived) の語彙として残す**。UI 表示・テスト記述の語彙は PP/PB/BP/BB を使い続けるが、保存されるのはセグメントの集合のみ
2. **写像の意味論を 2 種に分離する** (2026-07-10 コアレビュー C-1 で改訂: 当初の「全部 rate 写像」は物理隣接ペアでレーザー直線と着地点がズレる反例が出たため):
   - **OS 自動ペア (物理隣接)** = **物理投影**: 交点の物理 (mm) 座標を対向セグメントの物理 along へ射影して座標化する (範囲外は端へクランプ)。レーザー直線の継ぎ目連続点とワープ着地点が同一物理座標になることが整合条件で、pose が継ぎ目で整合していれば厳密に一致する
   - **ユーザセグメント (仮想接続)** = **物理長で正規化した rate 写像**: 交点位置を物理長 rate ∈ [0,1] に正規化し対向の rate へ写像。長さの異なる辺同士を意図的に比例対応させる意味論。logical 長でなく物理長を使うのは混合 DPI で写像が歪むのを防ぐため
3. **6cab429 の越境計算は「意味論の再導出」であって「値の golden 移植」ではない**: 敵対レビュー (2026-07-09) で、v2 の EdgeCrossingDetector は CG y-down の `event.location` を NSScreen y-up の frame と直接比較する y 反転バグ (V3 の init.mbt/core.mbt と同型) を持つことが実コードで確認された。したがって移植するのは 6cab429 が意図した意味論 (異軸ペアリング、targetSide 別の座標軸割当) のみとし、DR-0005 の CG y-down 規約の下で再導出して期待値は新規に計算する
4. **invertRatio (v2 の bool) は暫定維持、幾何導出への置換は実装時に検証**: モニタ pose (DR-0005) からセグメントの方向ベクトルを取れれば「向きの反転」は導出可能で bool フィールドは不要になる見込み。異軸ペアリングの全ケースが導出で賄えるかを、決定 3 で再導出したテストセットの上で確認してから置換する
5. **セグメント重複時の決定規則を仕様化**: 同一エッジ上で複数セグメントが交点を含む場合は「優先度リスト順で最初のもの」とする (V3 web UI プロトタイプで操作性を検証済みの方式)。v2 実装の `first(where:)` の暗黙配列順 (挙動未定義) を明示仕様に置き換える

## 遷移検出の入力契約 (BX / PX、DR-0004 のトリガーモデルと対)

- **PX (ネイティブ通過)**: 2 世代履歴の所属モニタ id が変化した。prev 点→current 点の線分と越境エッジの交点からセグメント・rate を求め、PP (何もしない) / PB (クランプ差し戻し) を判定する
- **BX (ネイティブブロック)**: current 座標がエッジ上 **かつ** delta の符号が外向き。エッジに沿う滑り移動と区別するために delta を併用する。BX は境界に押し付けている間連続発火し、その列が BP 速度推定器 (Phase 2) の入力になる
- **delta への依存は符号 (方向) のみに限定する**: CGEvent の deltaX/deltaY の大きさの意味論 (ポインタ加速度適用前後・量子化・クランプ持続中の値) は一次資料が曖昧なため、大きさに依存する契約 (意図座標の位置再構成) は置かない。エッジ上の接線位置はクランプ済み location から取る
- **検証の輪郭**: delta 意味論の実機マトリクス検証 (加速度 on/off × クランプ持続中 × ワープ直後 × 入力デバイス種別) を Phase 1 の検証タスクとして実施し、結果を findings に残す。OS のクランプがエッジ値ちょうどか 1px 内側かも同時に確認する

## 却下案

| 案 | 却下理由 |
|---|---|
| V3 の EdgeType enum を永続モデルにする | PB/BB の表現に「ブロック用の別リスト」等の追加構造が必要になり、v2 差分方式より状態が増える。enum は「2 集合の所属の組み合わせ」の派生値であり、正規化されたデータ (集合) から導出する方が矛盾状態 (enum と実リストの不一致) を型レベルで排除できる |
| クランプ前の意図座標を delta の大きさから再構成する契約 | delta の大きさの意味論が未検証・環境依存の疑いがあり、契約の前提にできない (上記)。符号のみなら方向判定に十分 |
| 3 段以上の連鎖越境を初期スコープに含める | v2 でも未実装。1 回のワープで目的モニタに到達する挙動を先に固め、連鎖は必要性が観測されてから (issue 起票で追跡) |
